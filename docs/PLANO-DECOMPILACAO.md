# The real decompilation plan

The goal is to have the game's code in C/C++ that, once compiled, produces **the same ROM
byte for byte** (a "matching" decompilation). This is the path that made the Pokémon Platinum
port possible. With it done, a native PC executable stops being a dream: it is a matter of
replacing the DS hardware layer (see Phase 7).

This plan is split into **phases**, each with **parts** of 1 to 5 days and a verifiable
"done" criterion. Phases 0 to 2 must go in order. From 3 on, the parts can be done in
parallel, and incrementally forever.

## Phase 0: "matching" build from the assembly (week 1) ✅ 0.1 to 0.3

Before writing any C, the ROM must be **rebuilt from the disassembled parts** and come out
identical. It is the safety net for everything else.

- **0.1 Tools.** Install `dsd`, `objdiff`, the `mwldarm` linker and a runner for the
  Metrowerks Windows binaries on Linux (`wibo` or Wine). The mwccarm compilers are not freely
  distributed; use the packages the DS decompilation community uses (decomp.me has the same
  ones). **Done when:** `mwccarm -version` runs. ✅ `decomp/tools/ferramentas.sh` (dsd 0.12.1,
  wibo 0.6.16, mwccarm from decomp.me); `objdiff` was replaced by `decomp/tools/comparar.py`
  for now.
- **0.2 Delink.** `dsd delink` cuts the ARM9 into object files (`.o`) per section. At first,
  one file per large region. **Done when:** the `.o` files are generated without errors. ✅
- **0.3 Linker script.** `dsd lcf` generates the `.lcf` for `mwldarm`; link everything and
  build with `dsd rom build`. **Done when:** `sha1(rebuilt_rom) == sha1(original_rom)`.
  ✅ `decomp/tools/montar_rom.sh` (the banner icon and the secure area CRC needed fixing; see
  [BUILD.md](BUILD.md#two-details-outside-the-code)).
- **0.4 CI.** A GitHub Action that runs the build, compares the SHA-1 and publishes progress.
  The ROM cannot go into the repository: CI only runs with the ROM in a secret, or on a
  machine of our own. **Done when:** a broken build turns the PR red.
  🟡 partial: without the ROM, CI checks the SHA-1 of each decompiled function
  (`conferir_sem_rom.py`) and publishes the progress (`progresso.py`, below, and the same
  numbers as an objdiff report, `progress_report.py`). The full build in CI is still open: a
  GitHub secret holds at most 48 KB and the ROM is 128 MB.

## Phase 1: identify the compiler and the flags (week 2) ✅ 1.1 and 1.2

Without the right compiler, no C comes out the same as the original.

- **1.1 Candidates.** From the SDK (NitroSDK 4.2, 2008), the candidates are mwccarm 2.0
  (service packs sp1 to sp2) and 1.2. Check which ones decomp.me offers for `nds_arm9`.
- **1.2 Test with known functions.** Compile `decomp/src/resource_hash.c` (function
  `0x02009b78`, 64 bytes) with each candidate and flag combination (`-O4,p`/`-O4,s`,
  `-proc arm946e`, `-thumb`, `-interworking`, `-enum int`, `-char signed`...). Compare with
  `objdiff`. The function is Thumb, so `-thumb` must be on.
  **Done when:** at least 3 different functions give a 100% match with the same configuration.
  ✅ `CExoString::CStr`, `HashResourceName` and the list item removal (`0x0202d428`): all
  versions 2.0, `-O4,p`. Full matrix: `decomp/tools/testar_compilador.sh`.
- **1.3 Per-library settings.** The SDK and NitroSystem were usually compiled with a
  different version and flags from the game's. Repeat 1.2 with one function from each library.
  Document in `docs/COMPILADOR.md`.

## Phase 2: separate the libraries (weeks 3 and 4)

A good part of the ARM9 is library code, which has public decompilations and does not need to
be rewritten from scratch.

- **2.1 NitroSDK.** Use the public NitroSDK decompilations, the same base as the Platinum
  port's `libntr`, to identify and name the `OS_`, `FS_`, `GX_`, `G3_`, `SND_`, `MI_`,
  `FX_`... functions. Generate signatures and apply them with `dsd sig apply`. **Done when:**
  the SDK functions are named and their `.c` files link with a match.
  🟡 562 functions named (`decomp/tools/nitrosdk.sh`, with the ntrtwl/NitroSDK 4.2.30001
  source, compiled as Thumb with 2.0/sp1p2); 86 of the 87 files already link from source
  with the ROM identical, including the parts in ITCM and DTCM. `gx_vramcnt.c` is missing,
  with one function that doesn't match: list in
  [BUILD.md](BUILD.md#nintendos-libraries-linked-from-source).
- **2.2 NitroSystem** (`NNS_G3d*`, `NNS_G2d*`, `NNS_Snd*`). Same approach.
  ✅ the region `0x020c8278`-`0x020d4394` is 100% NitroSystem 071126 (Thumb, 2.0/sp2), and
  its 59 files are linked from the compiled source with the ROM identical
  (`decomp/tools/nitrosystem.sh` + `decomp/tools/ligar_bibliotecas.py`).
- **2.3 C/C++ runtime (MSL).** `memcpy`, `__register_global_object`, exceptions, iostreams.
  Usually linking CodeWarrior's original `.a` is enough.
  🟡 the libraries are CodeWarrior 2.0 sp2's; 62 of the 68 MSL files the game uses already
  link from the `.o` files taken out of the `.a` (`decomp/tools/msl.sh`), with the ROM
  identical. Six are missing: list in [BUILD.md](BUILD.md#nintendos-libraries-linked-from-source).
- **2.4 File map.** Define in `delinks.txt` the boundaries of each "source file" (*translation
  unit*). The game was compiled file by file, and the classes help guess the split (e.g.
  everything of `CTlkTable` in a `TlkTable.cpp`). **Done when:** the build stays identical
  with the ARM9 split into TUs.
  🟡 153 pieces that certainly belong to a single file (**84%** of the game's code bytes,
  counting the 3 files already in C++) are already in `delinks.txt`, with the ROM identical
  (`decomp/tools/mapa_arquivos.py`, the rules of the strings and of the
  `__register_global_object` variables, in [BUILD.md](BUILD.md#the-games-file-map); DIARIO
  19, 21, 24 and 25). What is left are the edges and the files with no strings and no
  `Singleton`; each file's boundary is confirmed when the whole file is decompiled.

**Metric from here on:** % of code bytes that come from source with a match.
✅ `decomp/tools/progresso.py` (instead of `objdiff`'s report, which the project replaced
with `comparar.py`): reads `config/YWSE/` and, if present, the linker map; separates
libraries and game. `decomp/tools/progress_report.py` writes the same numbers in objdiff's
report format for progress trackers. The count is explained in
[BUILD.md](BUILD.md#the-progress-metric). Today: **14.91%** (libraries 87.71%, game 1.71%).

## Phase 3: Aurora engine core (weeks 5 to 8)

The base the whole game was built on. Starting here gives the most return, because these
functions are called everywhere.

| Part | Classes / functions | Why first |
|---|---|---|
| 3.1 Strings | `CExoString` ✅ (33 functions, `src/Aurora/CExoString.cpp`); `CResRef` does not exist in this version of the engine (resources are found by the hash of their name) | used everywhere |
| 3.2 Memory and singletons | ✅ allocator ✅ (`new`/`delete` with 5 pools and `NitroStartUp`, `src/Aurora/Memory.cpp`), `Singleton<T>` ✅ (`include/Aurora/Singleton.h`, with a virtual destructor: DIARIO 26), `CExoArrayList<T>` ✅ (except `DelIndex` for elements whose size is not a power of 2); `ResourcePool<T>` only exists as `ResourcePool<InventoryData>`, built inline in the inventory mode, and moved to Phase 5 (DIARIO 31) | a pattern repeated in hundreds of functions |
| 3.3 Files | 🟡 `CDSFileSystem`, `CErfMan`, `CErfTable` and `.small` reading ✅ (`src/Aurora/CDSFileSystem.cpp`, 45 functions, with `.data`, `.bss` and `__sinit`; the 7 template copies at the end stay in assembly, DIARIO 26); test with real data ✅ (`decomp/tests/test_arquivos.cpp`: the 8,689 resources of `test.herf` read by our C++, DIARIO 27); `FileReference` derives from `CGameBaseComponent` and moved to Phase 4 (DIARIO 28) | the format is already 100% documented |
| 3.4 Data | 🟡 GDA ✅ and GFF4 reading ✅ (`src/Aurora/G2DA.cpp`, 52 functions with `.data` and `__sinit`; the GFF4 functions in `include/Aurora/GFF4.h` are the ones the whole game uses; test with the 229 tables, DIARIO 29); text 2DA ✅ (`src/Aurora/C2DA.cpp`, 21 functions with `.data` and `__sinit`; test with the 370 item and spell tables, DIARIO 30); `CTlkTable`: 12 of 13 functions match and are checked in CI (`src/Aurora/CTlkTable.cpp`), `GetString` didn't match and the file still comes from assembly (DIARIO 28) | the formats are already documented |
| 3.5 Rules | 🟡 `CRules`: 8 of 9 functions match and are checked in CI (`src/Aurora/CRules.cpp`: the GDA table registry, `RandomRange`, `RandomFixed` and two `CExoArrayList<CExoString>` copies); `LoadRules` (0x1444 bytes, copies `combatrules.gda` and `creaturepositions.gda` into the file's globals) is missing, so the file is not linked yet; `StatInfos`, `StatRedirect` to do | the game rules the objects of Phase 4 read |

**Done when:** each part compiles with a match and has a test that reads real data. The test
is `decomp/tests/test_arquivos.cpp` (DIARIO 27): the C++ of `src/Aurora`, unchanged, compiled
on the PC and running on the ROM's files. It already covers 3.1 (`CExoString` in every name
and every path), 3.2 (the game's allocator serves every `new`), 3.3 and 3.4 (the 229 GDA
tables and the 370 2DA tables); the next parts go into it.

## Phase 4: game objects (weeks 9 to 14)

`CGameBaseComponent → CGameObject → CGameCreature / CGameItem / CGameSquad / CGameTrigger /
Placeable`, `ActionQueue`, `CGameEffect`, `InventoryData`, `CPlotManager`, `FileReference`
(came from Phase 3.3). The vtables are already mapped: each slot is a method to write.
Suggested order: `CGameObject` (base with 51 methods) → `CGameItem` (items) → `CGameCreature` → `Placeable` / `Puzzle`.

## Phase 5: game modes and interface (weeks 15 to 22)

`GameMode` and the 16 modes (`GameModeExplore`, `GameModeCombat`, `GameModeConversation`,
`GameModeChaoGarden`, `GameModeWorldMap`...), the `GuiManager` and the `.gui` screen system.
Combat is the biggest and most interesting one. Leave it until after Explore, which is
smaller. `ResourcePool<InventoryData>` comes in with the inventory mode (DIARIO 31).

## Phase 6: graphics, sound and the rest (week 23 onwards)

Background rendering (the `.cbgt` format is already decoded), `ModelManager` (`.nsbmd`
models), `VisualEffect`, `CMoviePlayer` (VX videos), sound. It ends when `progresso.py`
reads 100%.

## Phase 7: PC port (in parallel, from Phase 4)

Following the Platinum model: the game keeps calling the NitroSDK functions, and a new layer
implements them on the PC.

- **7.1** Compile the decompiled C for x86-64 with Clang/GCC, with the SDK replaced by
  *stubs*. **Done when:** it links, even if it doesn't run.
- **7.2** Platform layer: evaluate using `libntr` (it already translates the DS's 3D to
  OpenGL and emulates the 2D) or writing our own.
- **7.3** Input (mouse = touch screen), audio, saves.
- **Done when:** `sonic-chronicles.exe` reaches the title screen.

## How to work on a function (the daily cycle)

1. Pick a function from the `objdiff` report (start with the small ones, with a known class).
2. Read the assembly (`work/asm/`) and Ghidra's pseudo-C side by side.
3. Write the C/C++ in the right TU's file, with real names and types.
4. Compile and compare in `objdiff` until it reaches 100%. If you get stuck, create a
   *scratch* on decomp.me (`dsd objdiff --scratch` generates the links) and ask the community
   for help.
5. Update `symbols.txt` and the headers (`include/`) with what you learned.
6. Small commit: one function or a group of related functions per PR.

## Known risks

- **Compiler unavailable or wrong version.** That blocks everything from Phase 1 on.
  Mitigation: confirm early with decomp.me; the DS community maintains the compilers.
- **C++ code with templates and exceptions** is harder to match than C. Mitigation: start
  with the engine's C-like functions.
- **Legal question.** The repository never contains the ROM, the assets or the binary. The
  build requires the user's own ROM (as in pret/pokeplatinum).
